# خدمات (Khadamat)

**كل خدمة تحتاجها... في مكان واحد.**

منصة خدمات متعددة الأطراف، بواجهات مستقلة للعميل ومقدم الخدمة والإدارة، تدعم طلبات الخدمات المنزلية والصيانة والتوصيل والشراء والنقل والعمل الموسمي، مع متابعة الطلبات والتواصل والتقييمات وإدارة الكتالوج والتغطية الجغرافية.

## النسخة الحالية

**الإصدار 2.95** — وضع اختبار تلقائي بلا إعداد متغيرات OTP يدويًا، مع تحسين التنقل الداخلي في لوحة مقدم الخدمة.

- واجهات PWA عربية من اليمين إلى اليسار للعميل ومقدم الخدمة والإدارة.
- إنشاء الطلبات ومتابعتها، عروض الأسعار، المحادثات، الإشعارات، التقييمات والشكاوى.
- كتالوج ومناطق تغطية قابلة للإدارة، مع دعم بيانات الخدمات المحلية.
- تسعير المشوار من مسار قيادة حقيقي؛ إذا تعذرت خدمة التوجيه فلا يُستخدم الخط المستقيم بديلًا عن مسافة الطريق.
- إدارة الحسابات والصلاحيات وسجل التدقيق وإثباتات التسليم والملفات الخاصة.

## المتطلبات

- Node.js **22.18 أو أحدث**.
- npm.
- مساحة تخزين دائمة لقاعدة البيانات والملفات عند النشر.

## التشغيل المحلي

```bash
npm install
npm run build
```

انسخ `.env.example` إلى `.env` وعدّل الإعدادات المحلية. في بيئة التطوير المحلية، يمكن استخدام `NODE_ENV=development` و`WHATSAPP_OTP_ENABLED=false` للحصول على رمز اختبار. لا تستخدم هذا المسار في بيئة إنتاج فعلية.

### اختبار تسجيل الدخول على Railway دون إرسال واتساب مدفوع

أنشئ خدمة/بيئة staging منفصلة بقاعدة بيانات تجريبية، ثم اضبط متغيرات Railway التالية: `NODE_ENV=production` و`APP_ENV=staging` و`WHATSAPP_OTP_ENABLED=false` و`WHATSAPP_OTP_TEST_MODE=true` و`WHATSAPP_OTP_TEST_PHONES=+9677xxxxxxxx` مع استبدال الرقم برقم الاختبار الذي تملكه. اترك `WHATSAPP_OTP_TEST_PHONES` محصورًا في أرقام الاختبار فقط. سيظهر رمز الاختبار في استجابة طلب OTP ويُملأ تلقائيًا في الواجهة. لا تستخدم هذه الإعدادات في خدمة الإنتاج أو مع بيانات مستخدمين حقيقية؛ وضع الاختبار مخصص لاختبار حساباتك فقط، وقد يسمح لمن يصل إلى الخدمة بتسجيل الدخول إلى حساب رقم الاختبار. عند الإطلاق، استخدم `APP_ENV=production` وعطّل `WHATSAPP_OTP_TEST_MODE` وجهّز موفر WhatsApp Business الحقيقي.

ثم شغّل:

```bash
npm start
```

الواجهات والفحوص:

- `/` — واجهة العميل العامة.
- `/customer` — واجهة العميل.
- `/provider` — واجهة مقدم الخدمة.
- `/admin` — لوحة الإدارة.
- `/health` — فحص صحة الخادم.
- `/ready` — فحص جاهزية قاعدة البيانات.

يُطبّق الخادم الترحيلات ويضيف البيانات الأساسية تلقائيًا عند بدء التشغيل. بيانات العرض التجريبي اختيارية للتطوير فقط:

```bash
npm run seed:demo
```

حسابات العرض التجريبي، بعد تنفيذ الأمر أعلاه:

- العميل: `customer@demo.local` / `Demo12345`
- مقدم الخدمة: `provider@demo.local` / `Demo12345`

لا تستخدم بيانات العرض التجريبي على خدمة عامة.

## إعداد الإنتاج — قبل النشر

1. اضبط `NODE_ENV=production`.
2. اضبط `JWT_SECRET` عشوائيًا قويًا بطول 32 حرفًا على الأقل، وكلمة مرور قوية وفريدة في `ADMIN_PASSWORD`.
3. فعّل HTTPS واضبط `COOKIE_SECURE=true` عند تقديم الخدمة عبر HTTPS.
4. فعّل `WHATSAPP_OTP_ENABLED=true` وأدخل `WHATSAPP_ACCESS_TOKEN` و`WHATSAPP_PHONE_NUMBER_ID` وقالب واتساب صالحًا. إذا كانت ميزة OTP مفعّلة في الإنتاج دون بيانات المرسل، يرفض التطبيق بدء التشغيل. وإذا عُطّلت في الإنتاج، فلن يُصدر رمز تحقق تجريبيًا؛ سيرفض endpoint الطلب بدل تجاوز إثبات ملكية الهاتف.
5. في Railway، اربط Volume دائمًا واضبط `DB_PATH` و`UPLOAD_DIR` عليه. قاعدة SQLite والملفات المحلية ستفقد استمراريتها إذا بقيت على نظام ملفات مؤقت.
6. لا تضبط `TRUST_PROXY=true` إلا عندما يكون التطبيق خلف وكيل موثوق يضبط ترويسات العميل بنفسه.
7. اختبر استعادة نسخة احتياطية، وتدفق الطلبات الحقيقي، وتسجيل الدخول، ورفع الملفات على بيئة شبيهة بالإنتاج.

أهم المتغيرات موثقة في `.env.example`. لا تضع الأسرار الحقيقية داخل المستودع أو ملف ZIP الذي تشاركه.

## أوامر التطوير والتحقق

```bash
npm run typecheck
npm run build
npm test
npm run backup
```

`npm run test` يشغّل مجموعة الاختبارات في عمليات منفصلة. قد تستغرق المجموعة وقتًا بسبب تشغيل كل ملف اختبار في عملية Node مستقلة.

## البنية التقنية

- الخادم: Node.js وTypeScript باستخدام HTTP المدمج.
- قاعدة البيانات: SQLite عبر `node:sqlite`، مع migrations وطبقة وصول قابلة للاستبدال.
- الواجهة: TypeScript وCSS وHTML، دون إطار واجهات كبير.
- التخزين: ملفات محلية خلف واجهة `StorageProvider`.
- الوحدات: المصادقة، المستخدمون، الكتالوج، المواقع، الطلبات، المطابقة، عروض الأسعار، التقييمات، الشكاوى، المحادثات، الملفات، التتبع، الإشعارات والإدارة.
- الاختبارات: اختبارات تكامل ووحدات تحت `test/`.

## حدود النسخة الحالية

هذه نسخة مناسبة لتطوير MVP وتجربة تشغيل محدودة بعد إعداد بيئة الإنتاج، وليست منصة عالية التوسع جاهزة دون عمل إضافي:

- SQLite ومحدد المعدل والجدولة الموجودان في الذاكرة يفترضان تشغيل نسخة واحدة؛ التوسع الأفقي يتطلب PostgreSQL ومكونات مشتركة مثل Redis/Queue واختبارات ترحيل وتزامن.
- تخزين الملفات محلي؛ يلزم تخزين كائنات دائم عند التوسع أو تشغيل عدة نسخ.
- الدفع الحالي نقدي؛ بوابة دفع إلكترونية غير مفعّلة في هذه الحزمة.
- يعتمد تقدير المشوار على خدمة توجيه طرق متاحة ومهيأة؛ يلزم مراقبة التوفر وحدود الاستخدام.
- لم تُثبت الحزمة وحدها نجاح النشر الفعلي أو اختبار الواجهات على هواتف ومتصفحات متعددة. يجب إكمال فحص ما قبل الإطلاق في البيئة المستهدفة.

للتفاصيل، راجع `RELEASE_NOTES_2.88.md` و`TEST_REPORT_2.88.md` و`CHANGELOG.md`.


## فحص HTTP سريع للإصدار 2.89

بعد تشغيل التطبيق محليًا على منفذ 3000، نفّذ `npm run smoke:http`. وللفحص على عنوان أو منفذ آخر استخدم `SMOKE_BASE_URL=http://127.0.0.1:3189 npm run smoke:http`. يفحص الأمر صفحات العميل ومقدم الخدمة والإدارة، وملفات PWA الأساسية، وأصول الواجهة، ونقطتي الصحة والجاهزية.
